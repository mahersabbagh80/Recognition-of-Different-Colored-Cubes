Main training course · Lesson 11

Did fine-tuning help?

A new model file is ready. Before replacing the old one, compare what each finds—and what each mistakes for a cube.

Core: about 15–20 minutes · no training required

Your goal: design a fair comparison and explain whether the new detector meets a stated requirement. All results below are fictional teaching data, not measured project improvements.

1. Freeze the question before comparing answers

A baseline is the existing system used for comparison. A fine-tuned model starts with saved learned parameters and updates them using new training examples. A checkpoint is the file holding a saved model state. Comparing two checkpoints means comparing two learned versions, not simply two filenames.

Use the same labeled images, input preparation, and scoring rules for both. A label records the reference class and bounding box; a box is a rectangle locating a cube. A score cutoff decides which predictions are emitted. Fix it for this first comparison so a changed cutoff does not hide the effect of changing the model. Later, you can tune cutoffs on validation data and compare the resulting complete systems.

Training examples update the model. Validation examples guide choices, including which model or settings to keep. An untouched test set measures the selected system after those choices. Keep neighboring frames from a capture session—one recording under shared conditions—in the same split. New filenames alone do not create independent scenes.

Train candidates→Compare on validation→Select once→Assess on untouched test

2. Count the same way for both models

Intersection over Union (IoU) is shared box area divided by the area covered by either box. For this exercise, match predictions to references only when the class agrees and IoU is at least 0.50. Process higher scores first; match each prediction to its best eligible unused reference. A reference can be matched once.

A match is a true positive (TP). An unmatched prediction is a false positive (FP); an unmatched reference is a false negative (FN). Precision = TP/(TP+FP), the fraction of emitted predictions that match. Recall = TP/(TP+FN), the fraction of reference cubes found. A zero denominator is reported as undefined here.

Worked example: 8 matches, 2 extra boxes and 2 missed cubes give precision 8/10 = 80% and recall 8/10 = 80%. A second box on an already-matched cube adds an FP, not another TP.

Explore the comparison

A slice is a subset sharing a condition. The validation set contains 20 cube references in ordinary light, 10 in dim light, and a separate group of empty/look-alike scenes with no target cubes. Empty means no target cube, not necessarily no objects. Choose a slice to see what the overall number hides. Colored bar lengths show counts; text gives the exact values.

All supplied counts

Baseline: ordinary TP 18, FP 1, FN 2; dim TP 4, FP 1, FN 6; empty TP 0, FP 6, FN 0. Fine-tuned: ordinary TP 18, FP 1, FN 2; dim TP 8, FP 2, FN 2; empty TP 0, FP 2, FN 0. Add counts before calculating overall ratios; do not average slice percentages equally.

Notice the tradeoff in dim light: the fine-tuned model finds four more cubes but also adds one false positive. Ordinary-light results are unchanged. An overall improvement does not mean every error type improved.

3. Decide against a requirement

Suppose our demonstration requires recall of at least 80% across these validation scenes and at most three false positives in the empty/look-alike group. This is an illustrative requirement, not a universal quality standard. Inspect both conditions: finding more cubes is not enough if the detector also marks every colored bag.

Your decision

What the decision does not prove

It supports selecting this candidate on these validation examples. It does not establish performance on new camera conditions. Assess the selected system on untouched test scenes and inspect failures; if those failures guide another change, they become development evidence rather than an untouched final test.

4. Apply the comparison to our files

Keep a small run record: starting checkpoint, exact training images and labels, library version, settings, and selected output file. An epoch is a pass through the training examples; a training curve shows how loss or validation measurements change across passes. Inspect both curves and actual mistakes. A lower training loss alone is not the selection rule.

Optional: read the stopping and repeatability settings

The script supplies an epoch limit and patience, the allowance for epochs without validation improvement before early stopping. It also supplies cos_lr=True to vary the learning rate over training, and seed=42 to control random choices. Record these effective settings when comparing runs; a seed by itself is not a guarantee of identical results across hardware and software versions. See the training settings reference.

The fine-tuning script loads models/best.pt by default and copies its selected result to models/best_hardneg.pt. These are the two candidate checkpoints to identify explicitly. The prediction reporter draws and counts predictions, but does not match them against reference boxes. Its output alone cannot supply the precision and recall calculated above.

The current dataset configuration points validation and test at the same image directory. Before claiming an independent test result, prepare a genuinely separate labeled capture. Review labels visually, including empty-label crops, before using them as references.

Optional: run the real experiment later
  1. Record the baseline file, dataset version, capture-session split and matching rules.
  2. Choose one deliberate change, such as adding verified hard negatives (non-cube examples that resemble cubes). Keep a record of training settings.
  3. Run both checkpoints on the same labeled validation inputs. Compare matched counts and condition slices; retain example mistakes.
  4. Select the model and any cutoff using validation only, then evaluate the selected system on an untouched test capture.

No real training is launched by this lesson. Record effective library settings and version with each run. See the official training guide and validation guide when preparing a runnable workflow.

A robot may load a different artifact: an engine prepared for its inference runtime. Saving a new checkpoint does not automatically replace that deployed engine. The optional robot track explains that handoff.

Finish the main course

Write a four-sentence experiment plan: the problem you observed, the single change you propose, the data and rules you will hold fixed, and the evidence required to keep the result. Explain why your final test images have not guided that choice.

Self-check rubric

A complete plan identifies an observable failure, one controlled change, fixed validation inputs and rules, and both misses and false alarms as outcomes. It reserves a separate test for the selected system. “The loss got smaller” or “the file saved” does not meet that rubric.
