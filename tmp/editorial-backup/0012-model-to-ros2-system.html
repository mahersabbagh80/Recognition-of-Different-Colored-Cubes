1. The local ROS 2 vocabulary

Robot Operating System 2 (ROS 2) is middleware: software that lets independent robot components exchange data. Its graph is the set of named components and connections. A node is one participant in that graph. A process is an operating-system program. They are different ideas: one process can contain multiple nodes, and a launch system can arrange nodes into one or more processes. Do not infer process boundaries from node names.

A topic is a named stream of values. A publisher sends values to a topic; a subscriber asks to receive them. A message is one structured, typed value on that stream. A subscriber's callback is a function invoked when a message, or a synchronized set of messages, is ready. An executor is the ROS 2 scheduler that waits for ready callbacks and runs them.

Quality of Service (QoS) is the delivery policy for a publisher or subscriber. The useful local questions are: how many recent samples may wait in the queue, and should delivery be reliable (retry to deliver) or best effort (attempt delivery but allow loss)? A queue is waiting storage; a queue depth of ten means up to ten recent samples under a keep-last policy. Compatibility is checked for each publisher–subscriber pair: the publisher must offer what the subscriber requests. For example, a best-effort publisher cannot satisfy a reliable subscriber. Different settings can still be compatible. ROS 2 QoS compatibility reference.

The synchronizer pairing queue holds received messages while seeking timestamp matches. It is separate from the transport history controlled by QoS queue depth; changing one does not automatically change the other.

A timestamp is a time value attached to a measurement, usually recording capture time. Synchronization pairs observations that are close enough in timestamp. An approximate synchronizer uses a slop, the maximum allowed timestamp gap; it does not make two captures physically simultaneous.

Worked timing example: capture times of 5.000 seconds and 5.020 seconds differ by 0.020 s = 20 ms. Here s means seconds and ms means milliseconds; one second contains 1000 milliseconds. Under the following toy rule, a 30 ms slop accepts that 20 ms gap, while a 10 ms slop rejects it. Compare the gap with the allowed slop, not with either absolute timestamp.

2. The model and the deployment tools

The runtime path has several contracts. A model is a learned computation; training adjusts its parameters using examples. A saved model file is an artifact. A contract is an explicit agreement about a boundary's data, shape, units, and meaning. Preprocessing changes a camera array into the size, channel order, and numeric range expected by the model. A pixel is one image sample, and a channel is one colour or measurement plane in that sample. A tensor is a typed, shaped array used by a model. Inference applies the model to an input tensor. Decoding turns raw output numbers into class names, scores, and bounding boxes. A class is a category such as red_cube; a score supports a prediction numerically; and a bounding box is a rectangle locating an object in the image. A candidate is one possible prediction before filtering. Non-maximum suppression (NMS) is a heuristic that suppresses strongly overlapping boxes; it may also suppress nearby real objects, so it is a policy rather than proof of a duplicate.

A checkpoint is a saved model state that can be loaded for further use. In this project, .pt names the PyTorch checkpoint, .onnx names the portable graph, and .engine names the TensorRT target-specific plan. Precision describes how numbers are represented. FP16 is 16-bit floating-point representation; FP32 is 32-bit floating-point representation. A precision label describes the arithmetic format, not an accuracy guarantee. This numerical precision differs from evaluation precision, the fraction of accepted detections that are correct.

3. Latency, throughput, and stale queues

Latency is elapsed time from a frame's capture to its published result. Throughput is how many frames the system completes per second. Frames per second (fps) is that throughput unit. If a camera produces frames faster than inference can consume them, a queue grows. A stale frame is an old capture that waits so long that a newer scene would be more useful. A bounded queue limits waiting storage; it may drop old frames, which often protects freshness while reducing the number of processed frames.

Increasing throughput does not automatically reduce latency: a system can process many frames per second while an oversized queue makes each result old. The design choice depends on whether the consumer needs every frame or the newest useful frame.

Worked queue estimate: if 10 frames arrive per second and only 8 can be processed, the waiting count grows by 10−8 = 2 frames per second while space remains. An empty queue with 3 waiting slots fills in approximately 3/2 = 1.5 seconds. Processing three waiting frames at 8 per second takes 3/8 = 0.375 seconds. These are steady-rate estimates: they ignore bursts and other delays. If capacity meets or exceeds arrivals, this model predicts no growing backlog.

4. Find the first broken contract

When the final topic is empty, do not jump straight to retraining. Name the last boundary that still has trustworthy evidence, then test one hypothesis. A score threshold is the minimum score accepted as a prediction. The following explorer separates three depth-related symptoms that look similar at the output.

Failure explorer

Absent depth prevents the RGB/depth synchronizer from invoking the paired callback. Inspect topic presence and timestamps before inspecting model scores.

Static worked answers: absent depth blocks synchronization; a whole-image dtype/shape mismatch causes the current callback to return early; local insufficient statistics return KEEP with a low-quality reason; low scores point to the model/input/threshold boundary.

Applied to our cubes

Repository observationcube_detection_node subscribes to /depth_cam/rgb/image_raw and /depth_cam/depth/image_raw. Its configurable defaults declare an ApproximateTimeSynchronizer queue size of 10 and slop of 0.05 s. It receives camera intrinsics, the internal pixel parameters used for projection, from CameraInfo, the ROS message carrying calibration metadata. cv_bridge requests RGB as bgr8, meaning blue-green-red 8-bit channel encoding, and depth as passthrough, meaning retain the source encoding. The callback returns before inference when the whole depth array is not 2-D uint16: dtype means numeric data type, uint16 means unsigned 16-bit integer, and 2-D means rows and columns.

When the TensorRT engine is available, _infer letterboxes the RGB image, meaning it resizes while preserving aspect ratio and pads to a square, then runs the engine, decodes the output, and applies per-class NMS. 2-D means two image coordinates. The node then calls compute_geometry and publishes vision_msgs/Detection2DArray, a standard message containing a list of 2-D detections, on /cube_detections. It can also publish an interfaces/ObjectsInfo compatibility message, a project/vendor format retained for an existing consumer, and an annotated debug image, an image with boxes and labels drawn on it. If the engine cannot load, the current fallback publishes empty detections so topic wiring can still be smoke-tested; a smoke test is a quick connection or execution check, not a model-accuracy test.
